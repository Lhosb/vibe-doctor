## VERDICT: **APPROVE-WITH-CHANGES**

The test strategy is unusually good for a design document. §6.5's six golden rules are the work of
someone who has watched a golden get regenerated into a tautology, and Rule 2 — the algebraic
invariance gate against the *unmodified* pre-Phase-A goldens — is a genuinely excellent instrument
that I verified is achievable (§E.1). §3.4's three-tier planner proof correctly ranks its own
evidence and names the one assertion that cannot be faked. The design explicitly identifies where its
own gates are decorative (§6.3's fixture warning) and where a gate rests on a test double (Risk 4).

I am not approving it as-is for one structural reason: **several of the strongest gates in the plan
can only fail once, or cannot fail at all as specified.** Rule 2's parity gate is consumed by the
regeneration it precedes. The empty-models-dir proof has a passing control and no failing control.
The embedding-reuse assertion measures construction where the claim is about invocation. The golden
plan fixture, as described, is regenerated by the spec that asserts it. Each of those is a small
edit; together they are the difference between a plan that measures Phase A and a plan that
documents it.

Two of my findings overlap with the Spec Reviewer's independently-authored `spec.md` (M4 class
inversion, S7/S9 CI). I reached them separately and I am not restating their arguments — MF-6 and §B
below add the *test design* those findings ask for, and MF-7 and MF-9 are defects neither `spec.md`
nor `principal.md` records.

## MUST-FIX

*(A gate that is missing, that cannot fail, or that can only fail once.)*

### MF-1. Rule 2's parity gate deletes itself. It must be frozen as a permanent baseline, not run once.

§6.5 Rule 2 is the most important test in the plan and the design treats it as a *step*: "Both
comparisons read the *unmodified* Phase-A-era golden files. Only once this passes do you write the
new-shape goldens" (`principal.md:1069-1070`). After that write, the old values are gone from the
tree and the algebraic relation is unrecoverable — Rule 1 and Rule 2 are in direct tension, and Rule
1 wins.

**Why that matters beyond Phase A.** Rule 4 ("Phase B's gate is that the Phase A goldens re-run
unchanged", `:1083`) then inherits a baseline that was itself written *after* the change it was
meant to check. Every later phase's regression evidence traces back to numbers produced by the
refactor rather than numbers that predate it.

**What would have to be true for it to fail:** today, any change to the graph, output node,
frame reduction, class index, decode path, or plan execution. After regeneration: nothing — the file
and the code move together.

**Fix.** Commit the four current golden files unchanged, under a distinct never-regenerated path
(e.g. `spec/fixtures/mood_probe/golden/v0_1_0_baseline/*.json`), with a header comment stating they
are frozen pre-`v0.2.0` output and must never be rewritten. Keep the algebraic spec permanently:
four softmax heads `eq` the baseline; `(raw_emomusic - 1.0) / 8.0` within
`max(1e-4·|expected|, 1e-10)` of the baseline. It costs 6 KB of fixtures and it converts a
one-shot migration check into a standing gate.

### MF-2. The parity gate spans one of the four segments the ticket actually changes.

The dispatch asks whether a gate spans *Python output → gem typed value → mapper → MoodVector
column*. It does not. Verified current coverage of each segment:

| Segment | Covered today by | After Phase A |
| --- | --- | --- |
| Python raw → gem typed value | app golden spec, `spec/integration/essentia_extract_golden_spec.rb:38-71`; gem golden spec `spec/integration/essentia_golden_spec.rb:34` | Rule 2 covers this, and only this |
| gem value → mapper output | **nothing** (mapper does not exist) | §4.5 item 2 asserts the *declared range matches* — that is intent, not the composition |
| mapper output → `mood_vector.update!` attrs | `spec/jobs/enrich_album_job_spec.rb`, `spec/services/mood_grounding_service_spec.rb` — with **fabricated** `MoodProbe::Features` inputs (`mood_grounding_service_spec.rb:7-18`, per `inventory.md:283-289`) | those specs will not even load (see `spec.md` M6) |
| key-set agreement mapper ↔ `MoodVector::MOOD_HEADS` | **nothing** — confirmed absence, `inventory.md:291-300`, `:396-399` | still nothing |

**The cheap gate that closes segments 2 and 3 exists and the design misses it.** The frozen baseline
goldens from MF-1 *are*, by construction, the exact six numbers that reached `MoodVector` before this
refactor — the app golden spec reads `extractor.analyze(path).to_h`
(`essentia_extract_golden_spec.rb:38-39`) and that hash is what `MoodGroundingService` aggregates
(`mood_grounding_service.rb:93`, `:107`). So:

> A pure-Ruby spec, **no Docker, no Essentia, no models dir**: build an `Analysis` from the new-shape
> golden, run it through `MoodVectors::EssentiaMapper#call`, and assert the result equals the frozen
> `v0_1_0_baseline` hash — four heads exactly, valence/arousal within the existing tolerance — **and**
> that `result.keys == MoodVector::MOOD_HEADS`.

That single spec is the end-to-end parity statement the refactor needs, it runs on the dev Mac, and
it fails if the mapper drops the clamp, transposes a head, renames a key, or changes the rescale.
Add it to Phase A's DoD.

### MF-3. The empty-models-dir proof has a passing control and no failing control, asserts "succeeds" rather than a value, and has nowhere to run.

§3.4 assertion 3 (`principal.md:644-647`) is correctly identified as the only unfakeable proof. Three
problems, in increasing order of severity:

1. **It asserts success, not output.** "run `[:bpm]` with a deliberately empty models dir and assert
   it succeeds." A degenerate path that returns an empty `Analysis`, or a `bpm` of `0.0`, also
   "succeeds". Assert `analysis[:bpm].value` is finite and — on `clicks.wav`, which is a click
   train at exactly 0.5 s intervals (`spec/fixtures/mood_probe/audio/generate.sh:21-24`) — equal to
   **120 BPM** within tolerance. That is ground truth, not a golden (see §D.2).
2. **No failing control.** A green empty-models-dir run is equally consistent with "the planner is
   demand-driven" and with "model verification was skipped entirely." This team already has the rule:
   a bound with only a passing control proves nothing about whether it bites. Add the negative
   control in the same spec — `analyze(path, descriptors: [:bpm, :mood_happy])` against the **same
   empty dir** must raise `ConfigurationError` naming `msd-musicnn-1.pb` (or the head file). Also
   assert the models dir is still empty afterwards, so a silent auto-fetch cannot satisfy the test.
3. **It is specified as a gem-side spec and the gem has no CI at all** (§B). This is the single
   biggest structural gap in the plan and MF-3 is where it bites hardest.

**Fix.** Specify this proof as a **vibe-doctor** spec running inside the existing `essentia` CI job,
pointing `models_dir:` at a fresh `Dir.mktmpdir`. Verified feasible: the app image ships the six
`.pb` files (`.dockerignore:34-35` explicitly un-ignores `/tmp/essentia_models/*.pb`), so an empty
directory must be created rather than found — which is exactly the right shape for the test. This is
the only automated amd64 Essentia environment that exists (§B) and putting the strongest gate
anywhere else means it runs when someone remembers.

### MF-4. The embedding-reuse assertion measures graph *construction*; the claim is about *invocation*.

§3.4 assertion 2 (`principal.md:637-643`) extends the fake double to "record constructions in a file
keyed by `MOOD_PROBE_FAKE_TRACE`" and calls "exactly one MusiCNN entry after a
`[:mood_happy, :mood_sad]` run" the direct test of embedding reuse. It is not.

`TensorflowPredictMusiCNN.__init__` (`spec/support/fake_essentia/essentia/standard.py:26-29`) is the
constructor; `__call__` at `:31-34` is the inference. §4.1 builds the pipeline once per *process*
(`build_pipeline(plan, models_dir)`) and runs graphs per *file*. A Python rewrite that constructs one
MusiCNN and then invokes it once per head — the exact regression the planner exists to prevent, and
the one that costs real enrichment time — passes a construction-count trace unchanged.

**Fix.** Trace `__call__` as well as `__init__`, and make the assertion: for a request of N MusiCNN
heads over M files, the embedding is *constructed* once and *invoked* exactly M times, and each head
is invoked exactly M times. Add the multi-file case (`analyze_all` with 3 paths) — the design's
example is single-file, where invocation and construction counts coincide and the bug is invisible.

### MF-5. The golden plan fixture cannot fail on the Ruby side as described.

§4.2 item 3 (`principal.md:706-709`): "One committed JSON file, **generated by `plan_for` in a Ruby
spec** and consumed by a pure-Python unit test." If the Ruby spec generates it, the Ruby side is a
tautology — `plan_for` always agrees with its own output — and only Python can ever go red. The
stated purpose ("the only test that fails when someone changes the plan shape on one side only") is
then half-delivered.

**Fix.** Two artefacts, not one: a **generator** (`spec/fixtures/plan/generate.rb`, run by hand, in
the manner of `spec/fixtures/mood_probe/generate_goldens.rb`) and a **spec** that asserts
`plan_for(descriptors: [...]).to_json` `eq`s the committed file. Cover at least three plans: MusiCNN-only,
algorithm-only (`[:bpm]` — the `"graphs":[]` case at `principal.md:623-628`), and mixed. Add the
same anti-regeneration comment as MF-1. Python then parses the identical committed bytes.

### MF-6. Phase B's class-order defence is an "ideally", and the design does not say what *cannot* catch an inversion.

§6.2's watch item (`principal.md:1002-1004`) says a spec asserting `classes` matches upstream —
"**ideally** a checked-in copy of each `.json`". Risk 6 rates this the highest-consequence
silent-correctness area (`:1151-1156`). The Spec Reviewer independently reached the same conclusion
(`spec.md:197-216`); I concur and add the test design, because the dispatch asks specifically what
*will* catch an inverted head.

**What will not catch it, stated explicitly so nobody proposes them:**
- A range assertion. An inverted 2-class softmax head returns `1-p`, still a plausible float in `0..1`.
- A new golden for the new head. It pins `1-p` as expected forever — the canonical tautology.
- A complementarity check (`p(X) + p(non_X) ≈ 1.0`). It proves the two indices partition correctly
  and says nothing about which is which.
- A `plan_for` unit test asserting `take: {index: 1}` for `mood_relaxed`. It is derived from the same
  `classes` array it would need to check; transpose the array and the test moves with it. This is the
  trap, and it is the most natural test an implementer will write.
- Rule 4 (`:1083`). It protects the six *existing* heads and is silent on the five new ones.

**What will:**
1. **An independent copy of upstream truth.** Check in each `<head>-msd-musicnn-1.json` next to its
   `.pb` checksum, record its SHA-256 and fetch date in the registry row, and add a **non-network**
   spec asserting `Model#classes == JSON.parse(file)["classes"]` row-by-row. The JSON must be fetched
   from `essentia.upf.edu`, never derived from the registry, and the review must check each row
   against *its own* JSON — Risk 6's own instruction (`:1155-1156`).
2. **A semantic direction control where a robust prior exists.** `sine_440.wav` is a pure tone with no
   voice: assert `instrumental > 0.5` and `instrumental > voice`. `voice_instrumental` is precisely
   the head that (1) cannot express, since it has no positive class and therefore no "expected"
   orientation to transcribe wrongly *or* rightly — it needs a semantic anchor. Keep the margin wide
   (0.5, not a golden) so it is a direction gate and not a value gate.
3. **A one-time reviewable artefact.** In the amd64 image, emit *both* class probabilities for all
   nine heads over the four fixtures and attach the table to the Phase B PR. An inverted head shows
   up as a human reading `mood_sad = 0.98` on `sine_440.wav` and asking why. Cheap, and it is the
   only step that catches an error that is *correctly transcribed from an upstream mistake*.

### MF-7. The `allow_nan=False` design produces a different error taxonomy member than the design claims, and nothing in the plan crosses the serialisation seam.

§4.4 (`principal.md:766-769`) states: "A guard miss then raises `ValueError` inside the existing
per-file `try` and emits a proper `malformed_output` line."

**Verified against the code: it emits `inference_error`.** `mood_probe_extract.py:107-136` is one
`try` whose `except Exception` block (`:127-136`) emits `{"type": "inference_error"}`. The
`malformed_output` line is emitted only by the explicit non-finite branch at `:112-125`, which
`continue`s. A `ValueError` raised by `json.dumps(..., allow_nan=False)` inside `emit()` (`:126`,
`:68-69`) lands in the generic handler. Both are `TrackError` subclasses (`lib/mood_probe/errors.rb`)
so app behaviour is similar, but a spec written to the design's stated expectation will fail, and the
taxonomy claim in the acceptance criteria will be wrong.

**Fix, two parts.** (a) Decide and state which member a serialisation-time non-finite produces, and
if it is `malformed_output`, wrap `emit()` in its own `try` — do not leave the implementer to
discover it. (b) **Test it across the seam, not on either side of it.** This team has already
established that a mutation battery only proves what its seams cross: Python's default `json.dumps`
emits bare `NaN` and Ruby's `JSON.parse` rejects it (`security.md:64`, `:212-214`). The existing
harness is exactly right — `spec/support/fake_essentia/essentia/standard.py:52-55` produces
`nan-audio` / `infinity-audio` fixtures, exercised end-to-end through the real script and the real
Ruby parser at `spec/integration/python_seam_spec.rb:41-53`, with no Essentia and no Docker. Extend
it with:
- a **nested** non-finite at depth ≥ 2 (a `NaN` inside a `Vector`'s element list, and inside a
  `Categorical#distribution` value) — a top-level-only guard passes a flat test and fails here;
- `-Infinity` as well as `NaN` and `+Infinity`;
- an assertion on the **error class and message**, not merely `not_to be_ok` — the whole point is
  that today this path produces `BackendError: ... invalid NDJSON`
  (`lib/mood_probe/backends/essentia_python.rb:83-84`), which is the misleading outcome §4.4 exists
  to fix. Asserting only "it failed" cannot distinguish the fix from the bug.

### MF-8. The payload-shape contract has no negative tests — for either of its two halves.

Two contracts replace the deleted `Features` validation, and the design names both as properties
without naming a test that violates them.

**(a) Requested-set enforcement (Rule 3, `principal.md:1073-1081`).** This is the load-bearing
replacement for `Features#validate_keys!` (`lib/mood_probe/features.rb:29-35`), which today raises on
missing *or extra*. The design says "Say this explicitly in the spec, or it will be lost as a side
effect of deleting `Features`" — correct, and still not a test. Needs **two** negative specs against a
stubbed backend: a payload with an unrequested id, and a payload missing a requested id; each must
raise. The current gem suite has exactly these two, for the old contract
(`spec/extractor_spec.rb`: "raises SchemaError and stops later files when one file returns a missing
key" / "…an unexpected key") — they are the template, and they must not be deleted without
replacement.

**(b) `Vector` dimension.** §1.2's `Descriptor#shape` (200) and §2.2's `Vector#values` exist;
Security constraint 4 requires exact declared-dimension validation (`security.md:75`, `:173`); nothing
in §2.2, §4.3 or §6.1 says Ruby asserts `values.length == descriptor.shape`. `:musicnn_embedding` is
registered in Phase A (`principal.md:941-943`) with no acceptance criterion that requests it — so the
first construction of a `Vector`, the first 200-element recursive finiteness walk, and the first
~4 KB NDJSON record all happen unobserved. (Spec Reviewer M8 reaches the same place from the design
side.) Needs: a fake-double fixture returning a 200-float vector, and a *wrong-length* fixture (199
elements) asserting `MalformedOutputError`.

### MF-9. `verify!` is memoized on the extractor instance; descriptor-scoped verification makes that memoization a hole, and no test would catch it.

Verified: `Extractor#verify!` sets `@verified = true` and short-circuits on every later call
(`lib/mood_probe/extractor.rb:16`, `:19-24`), and `analyze_all` calls it unconditionally (`:35`).
Today that is safe because verification is whole-registry and argument-free. §2.1 changes the
signature to `verify!(descriptors: [...])` — "preflights only what the set needs"
(`principal.md:346`) — at which point memoizing a *boolean* is wrong: `verify!(descriptors: [:bpm])`
(which requires zero `.pb` files) would satisfy a later `analyze(path, descriptors: [:mood_happy])`,
and the missing-model `ConfigurationError` that `enrich_album_job.rb:8` depends on never fires. The
failure surfaces as an exit-2 backend error mid-run instead of a preflight abort — losing the
"fail before touching a file" property §3.1 item 3 lists as a reason for the whole planner design.

**Fix.** Phase A DoD gains: verification state is keyed on the descriptor set (or the resolved file
set), plus a spec — `verify!(descriptors: [:bpm])` then `analyze(descriptors: [:mood_happy])` against
an empty models dir must raise `ConfigurationError`. Pure Ruby with a stubbed store; runs on a Mac.
This interacts with `spec.md` M1 and should be resolved with it.

### MF-10. The sample-rate question has no gate, and no existing fixture can answer it.

Risk 1 (`principal.md:1109-1117`) and §8.2 correctly reduce "load audio once" to "once per required
sample rate" and flag `RhythmExtractor2013`'s required rate as UNVERIFIED. The dispatch asks what
test pins it once measured. The design names none, and §1.4's note and Risk 1 disagree on *when*
(`spec.md` S11).

**And the fixture corpus cannot support the measurement.** Verified with `ffprobe`: all four
decodable fixtures are **16000 Hz, 1 channel, 10.0 s**. Running `RhythmExtractor2013` "at 44.1 kHz"
against them means upsampling from 16 kHz — which tells you whether the algorithm *accepts* 44.1 kHz
input, not whether a genuine 44.1 kHz source gives the same answer. Production input is an iTunes
preview: ~30 s, 44.1 kHz, stereo AAC (`mood_grounding_service.rb:87-113`). The measurement as
specified would be made on material unlike anything the system processes.

**Fix — name all three, in Phase A:**
1. Generate one fixture at native 44.1 kHz via `generate.sh` (a click train at a known BPM), committed
   as WAV so it stays bit-reproducible.
2. The measurement: run `[:bpm]` on it at 16 kHz and at 44.1 kHz in the amd64 image; record both
   values and the delta in the phase's evidence.
3. The gate that pins the answer: `plan_for(descriptors: [:bpm, :mood_happy]).loads.map { it[:sample_rate] }`
   `eq`s the decided set (one entry if 16 kHz is acceptable, two if not) — a pure-Ruby spec — **plus**
   the ground-truth BPM assertion of MF-3 at whichever rate was chosen. Without (3) the measurement is
   a paragraph in a PR description that nothing enforces.

## SHOULD-FIX

**SF-1. The `essentia` CI job names one spec file and hardcodes its example count — new gates will
silently not run.** `ci.yml:117-123` runs `bundle exec rspec spec/integration/essentia_extract_golden_spec.rb`
and greps for `^${expected} examples, 0 failures$` where `expected = $(ls .../golden/*.json | wc -l) + 1`.
The count assertion is a good anti-silent-skip device and should be kept. But: (a) any new spec *file*
added by this work does not run at all; (b) adding examples to the named file breaks the arithmetic;
(c) MF-1's frozen-baseline directory would silently inflate `wc -l` if placed under `golden/`. Phase A
must update this job — widen it to a directory or a `--tag` selector, and derive the expected count
from something that does not move when fixtures are added. Put it in the phase DoD; it is the kind of
edit that gets discovered by a red build during a lockstep deploy.

**SF-2. The gem has no CI, and five of Phase A's six acceptance criteria live there.** See §B. Adding
`.github/workflows/ci.yml` to mood_probe running `bundle exec rspec` on `ubuntu-latest` is a few lines
and would cover the planner assertions, the golden plan fixture, `python_seam_spec.rb`, the registry
introspection spec, and the `no :series rows` tripwire — all of which need neither Docker nor Essentia.
(Concurs with `spec.md` S7; recorded here because it is the precondition for MF-3, MF-4, MF-5 and MF-8.)

**SF-3. Automate §6.2's falsifiability criterion.** "If Phase B requires touching
`mood_probe_extract.py` or any `lib/` file other than the registry, Phase A's design failed"
(`principal.md:990-993`) is an excellent instrument and currently a promise. It is a two-line CI check
on the Phase B branch: `git diff --name-only main...HEAD` must match only `lib/mood_probe/registry*`,
`spec/`, and model manifest paths. Make it a job, not a review note.

**SF-4. Bounded stdout/stderr readers are unit-testable today and should be specced when the
constraint lands.** `CommandRunner` retains complete stdout/stderr strings
(`lib/mood_probe/backends/essentia_python.rb:33-34`); `security.md:68` wants bounded readers with
kill-on-cap. This needs no Python and no Essentia — a fake command emitting `cap + 1` bytes, asserting
the reader stops, the process group is killed, and a specific error is raised. The existing
`spec/backends/command_runner_spec.rb` (44 lines, one timeout example) is the right home. Agree with
`spec.md` S3 that the *obligation* belongs at Phase E; the *spec shape* should be written down now so
it is not reinvented.

**SF-5. The fixture corpus is unrepresentative of production input, and one class of fixture must not
join the golden set.** All four decodable fixtures are 16 kHz mono WAV; production is 44.1 kHz stereo
AAC. A decode-path fixture in the production format is worth adding (it is the only thing that would
catch an `MonoLoader`/ffmpeg regression on real input). **But it must not carry numeric goldens** —
AAC encoders are not bit-reproducible across versions, and the gem's exact-`eq` gate
(`spec/integration/essentia_golden_spec.rb:34`) would become environment-dependent. Keep numeric
goldens on the synthetic WAVs; use the lossy fixture for "decodes, produces finite values, correct
error class on truncation" only.

**SF-6. Prefer ground truth over goldens wherever the fixture provides one.** `clicks.wav` is a click
train at exactly 0.5 s intervals (`generate.sh:21-24`) — **120 BPM by construction**. That is an
absolute assertion no regeneration can satisfy, and it is strictly stronger than any golden for `:bpm`.
`sine_440.wav` is A4, giving `KeyExtractor` a (weaker) expected `key == "A"` for Phase C. Note the
likely octave-error mode: if `RhythmExtractor2013` returns 60 or 240 on `clicks.wav`, that is a finding
to record, not a golden to update.

**SF-7. Every new tolerance needs both controls, recorded in the format the app spec already uses.**
§6.5 Rule 5 is right (`principal.md:1095-1098`). The existing precedent is
`essentia_extract_golden_spec.rb:22-23` — a comment recording that a 0.900e-04 `chirp.valence`
perturbation passed and 1.100e-04 failed. Keep that exact format (perturbation size, fixture, head,
outcome) and require it per *unit family*, not per descriptor: one control set for `:probability`, one
for `:bpm`, one absolute-tolerance set for `:lufs`/`:lu`. Rule 5's warning that relative tolerance is
meaningless for a dB quantity that can be near zero or negative is correct and worth keeping verbatim.

**SF-8. Decide `spec/support/phase3_parity.rb`'s fate explicitly.** It compares the gem against an
app-owned Python script that no longer exists (`inventory.md:277-281`) — it is already vestigial, and
MF-1's frozen baseline supersedes what it was for. Deleting it is defensible; leaving it broken
through Phase A is not. (Concurs with `spec.md` M6.)

**SF-9. Record *why* the two golden gates differ, in both files.** Rule 6 (`principal.md:1100-1103`)
is correct and is the kind of decision that gets "harmonised" away by a well-meaning cleanup. I
verified the two repos' golden JSON files are currently **byte-identical** for all four fixtures — so
the difference between the gates is purely the assertion (`eq` at
`mood_probe/spec/integration/essentia_golden_spec.rb:34` vs the relative-tolerance comparison at
`vibe-doctor/spec/integration/essentia_extract_golden_spec.rb:44-71`), which makes them look
redundant to anyone who has not read Rule 6. Put a one-line comment in each file: the gem asserts its
own determinism in a fixed image; the app asserts cross-environment reproducibility.

**SF-10 (TDD discipline — design phase).** There is no implementation and therefore no commit history
to assess; I record no TDD finding either way. For the implementation phase: MF-1's frozen baseline
and MF-2's mapper-identity spec are both writable **before** any Phase A code exists (they run on the
current goldens and need no Essentia), so Phase A has an unusually clean red-first entry point.
Expect them to appear in the first Phase A commit, and treat their absence as the flag.

## §A. Per-phase gate ledger

For each gate: what it catches, and — the question that matters — *what would have to be true for it
to go red*.

### Phase A

| # | Gate (`principal.md`) | Defect class caught | What must be true for it to FAIL | Verdict |
| --- | --- | --- | --- | --- |
| A1 | Algebraic parity vs unmodified goldens, §6.5 Rule 2 (`:1058-1071`) | any numeric drift from graph/node/reduction/class-index/decode/plan-execution change | a Phase A change moves a number — **once**; after regeneration, nothing | **Strong but single-use → MF-1** |

## §D. Fixtures

### D.1 Are the synthetic signals adequate?

**For Phase A: yes, and they are the right choice.** Phase A asserts *invariance*, not correctness —
whatever number the pipeline produced before, it must produce now. Deterministic synthetic input is
exactly right for that, and I verified the corpus supports the specific gate the design proposes:
all eight `valence`/`arousal` golden values across the four fixtures are strictly inside `(0, 1)`
(range 0.226–0.726, implying raw emomusic 2.81–6.81), so **no golden was produced by a clamp** and
Rule 2's `(raw − 1) / 8` algebra is well-posed on every one. That is the load-bearing precondition for
MF-1/MF-2 and the design does not check it.

**For Phase B (Tier 1 heads): adequate as regression gates, useless as correctness gates.** A golden
for `mood_sad` on white noise detects change and cannot detect inversion. This is exactly MF-6.

**For Phase C (BPM, key): the design's own assessment is right** — "*adversarial* for tempo and key —
only `clicks.wav` has any rhythm and none has a meaningful key" (`principal.md:1019-1021`). A pure
sine has no BPM; a swept chirp has neither BPM nor key; white noise has neither.

**For Phase D (loudness): not assessed anywhere.** A 10 s constant-amplitude signal is a degenerate
input for `LoudnessEBUR128`'s gated integration — the gating behaviour that makes the algorithm
interesting is only exercised by material with dynamic variation. Needs its own fixture.
