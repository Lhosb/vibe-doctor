## 2. Dispute rulings

### Dispute 1 — MF-3 part 3 (placement of the empty-models-dir proof): **CONCEDED.**

Ground (a) is straightforwardly correct: my premise was "the gem has no CI and no prospect of one",
and user decision 3 retires it. A finding built on a fact that has changed does not survive on
momentum.

**Ground (b) is the decisive one and I verified it rather than accepting it.** The claim is that
`RhythmExtractor2013` needs Essentia but no `.pb` file. Fetched
`https://essentia.upf.edu/reference/std_RhythmExtractor2013.html`: the algorithm's only input is
`signal` (`vector_real`), and its complete parameter list is **`maxTempo`, `method`, `minTempo`** —
three scalars, no filename, no graph, no path, no TensorFlow. Corroborated independently at
`https://essentia.upf.edu/reference/std_BeatTrackerMultiFeature.html` (the tracker
`method: "multifeature"` dispatches to): parameters `maxTempo`, `minTempo`, input `signal`, no model
reference. **The claim is true.**

It is also decisive, and the consequence is stronger than the revision states. In the gem the proof
runs from `Dockerfile.essentia` (`:1-15`, which already installs `ffmpeg` at `:6`, so `MonoLoader`
decodes) with **no `models fetch` step**, making it the only real-Essentia gate in the entire plan
with no runtime dependency on `essentia.upf.edu`. The gem's own golden spec does require the fetch —
verified in its header command block, `spec/integration/essentia_golden_spec.rb:1-8`
(`exe/mood-probe … models fetch && bundle exec rspec …`). So relocating the strongest gate to the app
would have added a dependency, not removed one, and §F.3's split of `essentia_offline` from
`essentia_golden` (`:596-604`) is exactly the right structure: it keeps the strongest gate free of the
one dependency that can make it flaky. That is a better answer than mine.

Ground (c) — gating gem behaviour in the app weakens Phase B's gem-only claim — is also right, and it
is the same argument M1 makes. The app-side mirror is kept and justified on its own terms
(`:577-580`): the app image ships the six `.pb` files (`.dockerignore:34-35`), so an empty dir there
must be *created*, which makes the mirror an integration-level claim rather than a duplicate.

**Ruling: CONCEDED on all three grounds.** Parts 1 and 2 stand as accepted.

### Dispute 2 — MF-6 item 2 (`sine_440` semantic direction control): **CONCEDED, with one condition.**

The question posed is fair: is a gate that can fail **for the wrong reason** better or worse than an
honest absence? My ruling: **worse**, and I am overturning my own item 2 on that basis.

The standard I argued in Round 1 was *a gate that cannot fail is not a gate*. The symmetric standard
is *a gate whose red does not identify a defect is not a gate either* — it is a coin flip wearing a
gate's clothes. A false red on `voice_instrumental` is uniquely expensive precisely because it is the
one head mechanism 1 cannot protect: the team has no independent signal to adjudicate it against, so
the observed human response to an unexplained red is to weaken or delete the assertion — and that
destroys the gate for real defects too. The Principal's characterisation of `sine_440.wav` is
verified: a 10 s 440 Hz pure tone (`generate.sh:6-9`; `ffprobe`: 16000 Hz, 1 ch, 10.0 s), far
out-of-distribution for a model trained on the Million Song Dataset. I asserted a semantic prior about
a model's behaviour on input unlike anything it was trained on. That was not evidence.

His sequencing is also strictly better process: measure inside mechanism 2's probability table, commit
the gate only if the observed margin supports it, record the observed value in the spec comment, and
if the margin is thin **write down plainly** that `voice_instrumental` has no automated correctness
gate and ships on human review (`:477-481`). That last clause is what makes this a concession rather
than a capitulation — it is the same "state confirmed absences explicitly" standard I applied
everywhere else, and §L Risk 2 (`:854-857`) already carries it as a named risk rather than burying it.

**The one condition.** "Measure first, gate second" must complete into an *artefact*, or it decays into
a deferred decision that never returns. Phase B's DoD needs a checkbox with exactly two acceptable
completions:

- the committed gate, with the measured margin in the spec comment; **or**
- a line in `voice_instrumental`'s registry `notes` reading, in substance, *"no automated correctness
  gate; orientation verified by human review of the Phase B probability table, <date>, <reviewer>"*.

"We measured and will decide later" is not a completion.

**And a way to earn the gate back, which I offer rather than just conceding.** Phase C adds a
deterministic musical fixture — §6.3's C-major arpeggio (`principal.md:1022-1023`). That fixture is
both genuinely instrumental *and* far closer to in-distribution than a pure tone, which is exactly the
combination `sine_440` lacks. Recommend Phase C re-run the direction control against it: if the margin
holds there, `voice_instrumental` acquires a real automated gate one phase later instead of never, and
§L Risk 2 downgrades. Cost: one assertion on a fixture that is already being added.

## 3. New evidence in my own scope — the sample-rate question is answered, not open

Verifying dispute 1 required reading `std_RhythmExtractor2013.html` in full, which turned up this.

**`principal.md:249-252` states:** "UNVERIFIED: the sample rate RhythmExtractor2013 must run at. The
Essentia reference page does not state a required input rate; 44100 is the conventional default."
`principal-v2.md` §L Risk 1 (`:850-853`) re-issues it as still standing and puts it on Phase A's
critical path. My own MF-10 accepted the premise.

**The premise is false. The page states it.** Verbatim, final sentence of the Description section of
`https://essentia.upf.edu/reference/std_RhythmExtractor2013.html`:

> "Note that the algorithm requires the sample rate of the input signal to be 44100 Hz in order to
> work correctly."

Independently corroborated at `std_BeatTrackerMultiFeature.html`: "the algorithm requires the audio
input with the 44100 Hz sampling rate in order to function correctly." It sits in the description
prose, not the parameter table, which is a plausible way to read the page and miss it.

**What this changes — three things, all in my scope:**

1. **§E.7 item 3's gate can be pinned now, at two entries.** The gate is specified as "one entry if
   16 kHz is acceptable, two if not" (`:519-521`). Documentation says 16 kHz is *not* acceptable, so
   `plan_for(descriptors: [:bpm, :mood_happy]).loads` pins to **two** sample rates (16 000 and 44 100).
   That is writable as a red test on day one of Phase A rather than blocked behind a Docker
   measurement — which matters, because §J.1's whole point is which specs are writable before the code
   exists.
2. **§L Risk 1 should be downgraded, not withdrawn.** The design consequence is settled: decision 4's
   "load audio once" is definitively false and §8.2's correction is now verified fact, not conjecture.
   What remains is a *cost* question ("is the second decode material for 30 s previews?"), which is
   measurement, not risk.
3. **The native 44.1 kHz fixture becomes more necessary, not less.** With the rate settled, the
   remaining honest question is whether upsampling 16 kHz → 44.1 kHz produces the same BPM as native
   44.1 kHz material. Every existing fixture is 16 kHz, so only the new fixture can answer it, and
   `clicks.wav`'s 120 BPM ground truth (`generate.sh:21-24`) gives both rates an absolute expected
   value. Keep the measurement (§E.7 item 2) — but reframe it from "what rate does it need?" to "does
   resampling change the answer?", which is a different and more useful experiment.

I flag this as **evidence supplied, not a finding against the revision** — the revision inherited the
UNVERIFIED marker from Round 1 and I did not challenge it either.

## 4. New defect introduced by the revision — in scope because it lands on MF-3 and MF-9

### NF-1. §B's `verify!` skips the environment preflight entirely for algorithm-only requests, which defeats half of MF-3's gate.

`principal-v2.md:215-223`:

```ruby
def verify!(descriptors:)
  required = plan_for(descriptors:).required_files   # Set<String> of basenames; [] for algorithm-only
  return true if required.subset?(@verified_files)
  model_store.verify!(filenames: required)
  backend.preflight!(plan_for(descriptors:))
  ...
```

For `descriptors: [:bpm]`, `required` is empty by the comment's own admission. An empty set is a
subset of every set, including `@verified_files` on the **first** call — so the method returns `true`
at line `:217` and **`backend.preflight!` is never reached**. An algorithm-only consumer gets no
environment preflight at all: not "python3 launches", not "Essentia imports".

**What breaks.** Today `verify!` → `backend.verify!` (`essentia_python.rb:89-101`) catches an
unlaunchable interpreter as `ConfigurationError` (`:49`) and a failed Essentia import as exit 2 →
`ConfigurationError` (`:61`), **before any file is touched**. §3.1 reason 3 names that property as one
of the four justifications for the whole Ruby-planner design, and §B invokes it two paragraphs above
this pseudocode (`:209-210`). Under the fix, a `[:bpm]`-only consumer discovers a broken Essentia
install mid-`analyze`, inside the timeout budget, once per file.

**Why it is my problem specifically.** MF-3's failing control exists because "a green empty-dir run is
equally consistent with 'the planner is demand-driven' and 'verification was skipped entirely'"
(quoted approvingly at `:589-590`). For the algorithm-only case, verification *is* now skipped
entirely — the exact condition the control was written to exclude. The file-verification half of the
pair still discriminates correctly (the `[:bpm, :mood_happy]` control has a non-empty `required`), so
MF-3's gate is not void; but its positive case no longer demonstrates what it claims.

**Fix — separate the two preflights, because they have different idempotence.**

```ruby
backend.preflight_environment!                       # once per extractor; boolean memo is CORRECT here
model_store.verify!(filenames: required) unless required.subset?(@verified_files)
backend.preflight_plan!(plan)                        # keyed on the resolved file set
```

**And the gate that proves it,** pure Ruby, Mac-runnable, and it **fails under the pseudocode as
written**: `Extractor.new(models_dir: Dir.mktmpdir, python_executable: "/nonexistent")` then
`verify!(descriptors: [:bpm])` must raise `ConfigurationError`. Add it to J.4 next to the MF-9
checkbox. This is the standard I have held everyone else to — a proposed fix should come with a test
that is red before it and green after.

**R1 — MF-1's baseline is frozen in one repo, and the gem's blocking golden gate loses its anchor.**
§E.1 gives a path but not a repo; §J.3 item 14 places `baseline_v0_1_0/` under vibe-doctor (`:767`);
§J.2 (gem changes, `:724-746`) lists no fixture work at all. I verified last round that the four
goldens are **byte-identical across the two repos**, so the gem's own goldens would be regenerated
with no frozen anchor — while §F.3 makes `essentia_golden` a **blocking** gem job (`:600`). Defensible
under Rule 6 (the gem's `eq` gate asserts *determinism in a fixed image*, not invariance, so a
post-refactor baseline is legitimate for it) — but that should be a written sentence, not an omission,
and freezing the same 6 KB in the gem costs nothing and would let the algebraic gate run in both
places. **Recommend: freeze in both; state explicitly which repo owns the invariance claim.**

**R2 — MF-10's gate and its fixture are specified in different repositories.** §F.3 puts the
sample-rate gate in the **gem's** `essentia_offline` job (`:599`); §J.3 item 15 lists the 44.1 kHz
fixture as a **vibe-doctor** new file (`:768`); §J.2 lists no gem fixture. A gate cannot run against a
fixture in another repo. `generate.sh` is byte-identical in both trees (verified Round 1), so the
fixture must be generated into both. Same applies to MF-3's click-train value assertion, which §F.2
homes in the gem. **Recommend: add a fixture line to §J.2.**

**R3 — the frozen baseline needs a stated retirement procedure.** A permanent invariance gate is a
permanent constraint. Under this plan nothing should legitimately move the six numbers (Rule 4 says so
for Phase B; Phases C–E add descriptors rather than change these), so it should hold indefinitely. But
the first legitimate cause — an upstream model-version bump — will make the gate an obstacle, and the
observed response to an obstacle with no documented exit is deletion. **Recommend one sentence in
§E.1:** retirement is a new dated baseline directory, the old one kept, the rationale recorded in the
commit — never an edit to `baseline_v0_1_0/`.

*(Minor, no action needed: §J.1 says the baseline freeze and the mapper-identity spec are both
"writable before any Phase A code exists" (`:720-722`). The freeze genuinely is — it is a file copy.
The mapper spec is writable **red** but cannot go green until Phase A produces the new-shape golden,
since seeding its input from the baseline would make it circular. That is ordinary red-first TDD and
the DoD framing is fine; noting it so an implementer does not read `:722` as "both should be green in
commit one".)*
